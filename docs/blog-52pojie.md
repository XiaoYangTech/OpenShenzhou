# 【原创】把 Windows 本地神经语音引擎整个"拆"出来：OpenShenzhou 复刻记（过程·取舍·踩坑）

> 关键词：EdgeTTS / Windows 自然语音 / ONNX / INT8 / 逆向 / 流式推理 / 语音合成 / 韵律断句
>
> 这是一篇"过程贴"：不只讲结果，更讲**每一步为什么这么做、试错过什么、最后怎么验证**。
> 文末附微软亚研（MSRA）的参考论文——这个引擎的架构和它们高度同源，读论文能少走很多弯路。

---

## 0. 先说结论（以及它为什么值得做）

现在的开源 TTS 生态里，大家常用两种"微软音色"：

1. **在线 Edge TTS**（`edge-tts` 一类工具）：调微软云端接口。音质好，但**必须联网**，
   会限流、会 401/403、接口说变就变，离线/内网/嵌入式场景直接歇菜。
2. **Windows 本地语音 + SAPI 转接器**（如 NaturalVoiceSAPIAdapter）：能离线，
   但**只能 Windows**，要注册 SAPI，核心推理引擎是闭源 DLL，模型还是加密的 `.bin`。

我们的目标是第三条路：

> **不注册 SAPI、不调用微软 DLL、不联网**，直接加载 Windows 语音包（appx）里的模型，
> 用 ONNX Runtime 在任意平台跑出**和官方逐采样一致**的音频。

最终做到：模型层最大误差 ~1e-6、相关 1.0000000；8 种语言 23 个音色包；中文常见句整句音素一致率
从 48% 一路提升到 **97.7%（585/599）**（599 句 held-out，逐 id 一致）；词界后处理（断词类别 → 词序列）在留出集上 585/599 句与引擎完全相同（97.7%），残余 14 句是长尾拆分差异；再往前一步：把引擎内部的多音字读音 CRF 也离线复刻了，应/为/将/中/只/地/杆等 80 个模型参与决策；
CPU 上 8.8 倍实时、内存 375 MB、无任何 Windows 依赖。

为什么强调"逐采样一致"？因为只有一致，才能把它当作**官方引擎的开源替身**：
替换进现有系统时，不会因为音质/时长/发音细节差异引入回归，测试也才有客观标准——
很难说清"听起来差一点"，但 `max|Δ| < 1e-6` 是可以说清的。

## 1. 第 0 步：先搞清楚"敌人在哪"

Windows 本地自然语音在系统里的落点是：

```
Microsoft.CognitiveServices.Speech.extension.embedded.tts.dll      # 5.9 MB，x64
Microsoft.CognitiveServices.Speech.extension.onnxruntime.dll       # 它静态/动态链接的 ORT
```

语音包（appx 解包后）里是：

```
am_v5_encoder.bin                 2.1 MB
am_v5_decoder.bin                 0.7 MB
device_vocoder_v6_streaming.bin   2.3 MB
phones.txt / punc.txt             音素与标点符号表
MSTTSLocZhCN.dat                  48.9 MB   ← 中文前端资源（词表/读音模型）
```

**为什么先做静态侦察**：在没有源码的情况下，先确认"哪部分闭源、哪部分只是数据"。
结论很关键：**闭源的是代码，模型本身是标准 ONNX**——这就决定了后面所有技术路线。

## 2. 第 1 步：拿到明文模型——为什么不硬逆加密算法

`.bin` 熵接近 8，看起来像加密。第一反应是逆它调用的 `bcrypt`（AES）——确实钩到了
`BCryptGenerateSymmetricKey`，但很快放弃了这个方向，原因有两个：

1. 逆密钥派生链条很脆弱，换个音色包/版本就白干；
2. **更本质的一点**：不管容器怎么加密，引擎最终一定得把**明文 ONNX protobuf** 交给 ONNX Runtime。
   与其逆加密，不如直接 Hook 它的终点。

### 2.1 Hook OrtGetApiBase

ONNX Runtime 的 C API 只有一个导出：`OrtGetApiBase()`，返回 `OrtApiBase`，
再 `GetApi(version)` 得到一张 `OrtApi` 函数表。我们的做法是：

- 把 `GetApiBase` 补丁掉，返回一张**假的函数表**；
- 假表里只改写我们需要观察的槽位：`CreateSessionFromArray`（拿模型指针+长度）、`Run`（拿输入输出）；
- 其余槽位原样转发。

这样引擎在正常流程里把模型指针交给我们时，直接 `memcpy` 落盘即可——**与容器格式完全解耦**。

> 为什么这个思路值得强调：逆向工程里最省力的方案往往不是"正面破解算法"，而是
> "找到系统里那个不得不出现的明文/中间态，在那里截流"。模型→ORT 就是那个中间态。

### 2.2 然后才回来看 `.bin`：原来只是 XOR

拿到第一个明文 ONNX 后，剩下的工作变成"已知明文攻击"：

- 取 `.bin` 和对应明文 ONNX 异或，发现异或结果以 **90 字节为周期循环** → 不是加密，是 XOR；
- 90 字节 key 直接读出来：
  `ZCjZ7nHDSLvf4gpELteM4AnzaWUjTpn7UkV7D@vvksl0w1SNgon6d1905WANbktDc9S39oaA4r29HJNayXvTq8fJsq`
- 23 个语音包交叉验证：全都用同一把 key，格式统一为
  `40 字节头 [16B hash][16B 0][u32 载荷长度][u32 0] + XOR 载荷`。

后来复盘：**先用最笨的钩子拿到一个样本，再回头找规律**，比一上来就死磕加密算法快得多。

## 3. 第 2 步：8 个私有算子——为什么必须"语义等价"

明文 ONNX 里有 8 个 `test.customop` 私有算子：

| 算子 | 用途 |
|---|---|
| `StreamingConv` | 带 2 帧历史缓存的卷积 |
| `StreamingConvTranspose` | 带缓存的转置卷积 |
| `StreamingAdd` | 两路流式张量按"低延迟优先"对齐相加 |
| `StreamingPad` | 带控制输入的补零（首块/中间块/收尾块不同） |
| `StreamingSplit` / `StreamingSlice` | 流式切分 |
| `StreamingGather` | 流式索引 |
| `StreamingRound` | 跨 chunk 一致的量化取整 |

如果只是"能出声"，把这些算子换成"近似实现"（比如普通因果卷积）也能跑。**但我们要的是逐采样一致**，
而流式推理里任何一点语义偏差都会**沿时间轴累积**：缓存少 1 帧、补零方向错、块边界处量化不一致，
几句话之后就是完全不同的音频。

### 3.1 怎么确定语义：不是猜，是"对拍"

我们保留了引擎本体作为**对照实验台**：同一个音素序列，一边让引擎跑，一边让我们的图跑，
逐层比较中间张量。几个关键坑：

- `StreamingConv`：缓存是 2 帧，首块左侧补 `[0,0]`，中间块补 `[0,0]`，**收尾 flush 块补 `[0,1]`**，
  而且首块输出要做切片——这三种模式必须分开实现；
- `StreamingAdd`：低延迟分支要先对齐，首块直接截断、中间块拼接后截断、flush 块不截断；
- 逐 chunk 量化：引擎每解完一块就做一次 `Round` + 缩放，**跨块也必须保持同样取整**；
- ONNX 图里的 `Conv` 本来是非因果的，重写时必须手动改成因果补零。

### 3.2 为什么"每块单独建静态图"

ONNX Runtime 对动态 shape 的支持有限，尤其我们这种带控制输入、缓存读写、切片位置随块变化的图，
符号 shape 一冲突就报：

```
'onnx::Add_164_g2' is not a graph input
```

试过统一动态图、试过 pad 到固定长度，都不稳。最后改成：**按块类型/长度分别生成静态 shape 的 ONNX 模型**，
每个图只负责一种块（64 帧、32 帧、flush……），运行前按调度选图。代价是图变多，收益是彻底稳定、且能逐位复现。

### 3.3 流式调度的发现过程

一开始不知道引擎怎么切块，只能"看"：在 `Run` 钩子里记录每次 decoder 的输入长度，跑不同长度的句子：

```
第一块  32（句子很短时）或 64
之后：剩余 >64 → 切 64；剩余 >32 → 切 32；最后一块 flush
每块解完立即量化，再进 vocoder
```

把这些抄进我们的调度后，**中间结果和最终音频都对上了**。

## 4. 第 3 步：前端才是真正的深水区

模型只负责"发声"，读什么、怎么断、多音字怎么念，全在前端。不同语言的输入格式完全不同，比如中文：

```
-bos- br0 <音节> - <音节> ... br1 <音节> ... br4 punc。 ~
```

- `-` 音节分隔；`br1` **韵律词边界**；`br3` 逗号级停顿；`br4` 句末；`punc。` 标点；`~` 结束。
- 英文/法/德/西/葡也用同一套 frame 格式；日文 Keita、韩文 InJoon 又是另外两套；葡语 Francisca 是平铺音素流。
- 更麻烦的是：**符号 ID 每个音色包都不一样**（中文两个音色只有 62/193 个 ID 相同，日文只有 3/130，
  葡语 0/224）。所以所有标定数据必须以**符号名**存储，运行时按目标音色包映射。

### 4.1 为什么用"引擎当老师"而不是写语音学规则

中文前端的三座大山：

1. **词表**：引擎内部有一个很大的词表，同一个字在不同词里读音不同；
2. **多音字**：约 200 个常见多音字，靠上下文决定读音；
3. **韵律断句（br1）**：不是普通词边界——同一个"忘记"，单独读是一个词，
   放进"会议室的灯忘记关了"里，引擎会在"忘""记"之间插 br1。这是它的统计模型决策的。

手工写规则不可能覆盖。于是我们换了个思路：**让引擎自己当标注器**，把它的输出批量采集下来，
再用这些数据训练/校准我们的前端。

### 4.2 关键一招：让引擎"只跑前端"

正常合成一句要 1.4 秒，采 10 万句要 40 小时。我们做了个探针：

1. 钩住 `OrtApi::Run`；
2. **encoder 的 Run 正常跑**（它的输入就是我们要的音素 id 序列）；
3. 之后的 decoder/vocoder 的 Run **直接返回一个 ORT 错误状态**（用 `CreateStatus` 造一个 status），
   引擎立刻放弃后续计算；
4. SAPI 返回错误，但 encoder 输入已经落盘。

效果：**约 15 句/秒，比完整合成快 20 倍**，两个进程并行就能到 20+ 句/秒。
用这个办法把中文语料（Windows 系统里的文本资源）采成了「文本 → 引擎音素序列」的数据集，
这是后面所有前端工作的地基。

> 为什么这个技巧值得单独讲：它把"不可见的内部状态"变成了"可批量获取的监督信号"，
> 成本从"40 小时"降到"2 小时"，可行性完全不一样。

### 4.3 词表与读音

- 从引擎数据里标定出 **78,962 条核心词条**（每条含引擎真实分词结构与读音）；
- 从成语库、短语词典、歌词里再补 **41,455 条**生僻/成语词条（逐条送入引擎实测）；
- 全 CJK 基本区 **20,600 个汉字**的单字读音表（引擎实测）；
- 1,375 条「拼音 → 音素」映射（用实测数据反推，修掉了 iong/ei 等规则映射错误）；
- 215 个多音字的上下文读音表（7.2 万条 n-gram）。

顺带修正了一个典型坑：不同音色包的符号表不同，所以这些表全部以**符号名**存，
运行时再 `name → id` 解析。

### 4.4 韵律断句（br1）：先代理，后官方

br1 是韵律短语边界，由引擎内部的统计模型逐句预测。我们做了两件事：

1. **代理模型**：用 4.8 万句引擎标定数据训练"字间隙是否断词"分类器
   （哈希特征 262,144 维 + 逻辑回归，特征含上下文 n-gram、词表命中、词典分词基底等），
   把中文 held-out 整句音素一致率从 49.7% 提到 72.8%；
2. **官方模型逆向**：在 `MSTTSLocZhCN.dat` 里找到 87 个 CRF 模型段，解出了完整容器格式
   （见第 6 节），确认它们是**多音字读音模型**；br1 的真正模型还在追（候选是
   `CCRFBreakTagger` / `CBlstmWordBreaker` / `CNeuralCRFWordBreaker` 这类组件）。

为什么先上代理模型？因为 br1 只是前端的一部分，而"模型层逐采样一致"已经可以先落地验证；
代理模型用同一批官方标注训练，能显著缩小差距，同时为官方模型逆向争取时间。

### 4.5 数字、符号、多音字读法

按引擎实测规则补了 `tn_symbols()`：

| 输入 | 引擎读法 |
|---|---|
| `5℃` / `-5℃` | 五摄氏度 / 零下五摄氏度 |
| `￥100` / `$100` | 一百元 / 一百美元 |
| `5～10` | 五至十 |
| `3×4` / `10÷2` | 三乘以四 / 十除以二 |
| `99.9%` | 百分之九十九点九 |
| `2026/10/26` | 二零二六年十月二十六日 |
| `9:30` | 九点三十分 |

9 项实测 7 项与引擎逐 ID 一致；英文混排（`abc@qq.com`）、`#`、电话号码分组、`·` 间隔号还在补。

## 5. 结果：我们和官方到底有多像

**模型层（输入音素序列一致时）**：

| 语言 | 最大绝对误差 | 相关系数 |
|---|---|---|
| 中/英/法/德/西/葡/日 | ~1e-6 | 1.0000000 |
| 韩 | 1.3e-4 | 1.0000000 |

误差来自浮点累加顺序差异，听感完全一致。

**前端（中文）**：599 句 held-out 句子，首句整句音素 id 完全一致率：

| 阶段 | 一致率 |
|---|---|
| 早期 SDK（规则 + 标定词表 + 哈希分词） | 82.5% |
| 复刻官方断词网络（未调后处理） | 89.6% |
| + 词起始规则 + 官方词表相邻合并 | 91.0% |
| + 学习版「引擎合并率」表 | 93.8% |
| + 未见词默认合并 0.5 | 94.7% |
| + 句尾标点规则 | 95.3% |
| + 「一」变调规则 | 95.7% |
| + 多音字 CRF 离线复刻 | **97.2%（582/599）** |

而且断词网络是**逐字节精确复刻**：进程内 hook 抓引擎 `CBlstmWordBreaker` 的逐字类别，
与自研前向对比 **325/325 字符 100% 相同**；纯汉字留出集词界整句一致率 98.27%。

**性能**：4 核 CPU，RTF 0.113（约 8.8 倍实时），内存约 375 MB，模型共约 5 MB。

## 6. 顺带把模型结构也看清楚了（和论文对得上）

把三套 ONNX 的算子表打印出来，架构其实很清晰：

**Encoder（2.1 MB）**：输入音素 id + `speed_ratios`，输出"扩展后的帧级隐状态"和"每个音素的时长"。
里面有 13 个 k=3 卷积、4 个双向 LSTM（hidden 128），以及 `CumSum` / `Range` / `If` / `Sigmoid`——
这就是 **时长预测器 + 长度调节器（length regulator）**，和 FastSpeech 2 的 variance adaptor 思路一致。

**Decoder（0.7 MB）**：输入帧级隐状态 + 两层 LSTM 的 `h1/c1/h2/c2` 状态，
输出 80 维 mel + 新状态；6 个 k=3 卷积 + 2 个 LSTM（INT8）。
说明它的声学解码是**帧级流式 RNN**（带状态缓存），而不是 FastSpeech 那种一次性并行 Transformer——
这是为了流式合成做的取舍。

**Vocoder（2.3 MB）**：输入 mel `[1,80,T]` + 两个 GRU 状态，输出波形；
WaveNet 式空洞卷积（k=3，dilation 1/3/9，另有 k=7 前置、k=63 后置），
4 个转置卷积完成 256 倍上采样，`LeakyReLU`，逐块流式缓存。

量化方式：encoder/decoder 用 **动态 INT8**（`DynamicQuantizeLSTM` / `MatMulInteger`），
vocoder 为 FP32。这与微软亚研在端侧轻量 TTS 上的路线一致：

- **FastSpeech / FastSpeech 2 / 2s**（MSRA & 浙大）：
  <https://arxiv.org/abs/2006.04558> —— 非自回归 TTS、variance adaptor（duration/pitch/energy）、
  FastSpeech 2s 的 text-to-waveform 思路；
- **LightSpeech**（MSRA）：<https://arxiv.org/abs/2102.04040> —— 面向端侧的轻量 TTS（15× 压缩、6.5× CPU 加速），
  我们看到的 INT8 小模型正是这条路线；
- **NaturalSpeech**（MSRA）：<https://arxiv.org/abs/2205.04421> —— 端到端高质量 TTS；
- **MSRA 教程**：Pushing the Frontier of Neural TTS（ISCSLP 2021）
  <https://www.microsoft.com/en-us/research/uploads/prod/2021/07/ISCSLP2021-TTS-Tutorial-Xu-Tan.pdf>；
- **Efficient ML for Speech and Music**（Xu Tan）
  <https://www.microsoft.com/en-us/research/wp-content/uploads/2021/07/Efficient-ML-for-Speech-and-Music-Xu-Tan.pdf>。

> 这些论文对理解引擎行为很有帮助：例如为什么模型这么小、为什么有长度调节器、
> 为什么端侧要做 INT8、为什么流式实现要用因果卷积+缓存。逆向时"猜结构"就可以少很多。

## 7. 前端模型逆向：目前挖到哪了（过程记录）

br1 的模型不在 `MSTTSLocZhCN.dat` 的 87 个 CRF 里（那些是多音字读音 CRF）。
我们的排查过程：

1. 解析 `.dat` 结构：40 字节头 + 资源段；每个 `TD\0\0` + GUID 段是一个模型容器；
2. 解出 87 个 CRF 的完整格式：

```
TD\0\0 | GUID | 长度 | 常量 | "CRF\0" | ver=100 | size | nFeatures | nLabels | nTemplates |
lenA | lenB | hsz(=L²×4) | 1.0f | 0.0f | 标签串偏移×L | 模板串偏移×T | A段 | B段 | C段
```

- 每个模型有自己的 UTF-16 字符串表（`U00:` 位置 − 模板[0]偏移 = 表基址）；
- 标签就是候选读音（如「卷」的三个标签：juǎn/juàn/quán）；
- **A = 特征索引结构，B = 权重（float32，每项 L 个、成 ± 对），C = L×L 转移矩阵**；
3. 运行时验证：用 ctypes 直接读引擎进程内存，找到 **113 个已解析模型对象**，
   其数据块与 `.dat` 中对应段**逐字节相同**（模型 8：A/B/C 在堆里连续排列，长度 460/296/16，
   正好等于 `.dat` 的 lenA/lenB/hsz）。至此官方读音 CRF 已经"可导出、可复刻"。

**真正的 br1 模型找到了：`CBlstmWordBreaker`（LSTM 双向断词）。**

判断链路：
1. 语音包 `.dat` 开头就有一块 5.6MB 的模型块（`+0xD8` 头：`offLayers/offX/offEmbedding/rows/cols`）；
2. 运行时找到 `CBlstmWordBreaker` 对象，其权重指针 = `dat+0x41868`，rows=20,947、cols=64；
3. 层结构：BLSTM + DNN，配置在 `dat+0x130 / 0x41030`，前向/反向 LSTM 权重在 `0x5C0 / 0x20D30`；
4. 用 Ghidra 把乘加内核（`FUN_180267a70`）和 LSTM 单元（`FUN_1802368dc`）逆出来，
   确认 `y = W·x + b`、门序 `[i,f,g,o]`、权重按列优先存储。

**怎么证明"精确复刻"**：直接在引擎进程里注入 hook——
把向量 erase 函数入口改成跳转到自建 shellcode，记录每次调用的
`(返回地址, vector 指针, start, count)` 并把 vector 内容拷到固定内存区；
合成一句中文后读回来，就得到**引擎内部逐字类别**。对比结果：

```
engine: 0 2 0 2 0 2 0 2 3 2
ours  : 0 2 0 2 0 2 0 2 3 2     ← 325/325 字符全部一致
```

**后处理**（类别→最终词）也复刻了：
- 统计发现「类别 0/3 = 词起始、1/2 = 词内延续」，
  所以词界 = 在 `class∈{0,3}` 的字符**之前**切（不是教科书 BMES 的解码方式）；
- 切完再按官方词表做相邻词合并，合并与否用**引擎语料统计出的每词合并率**决定
  （例：「用于」引擎常拆开→不合并；「备份」常合并→合并）。

**日语同理**：8 种语言里只有中文和日语用 `LSTMWordBreaker`。
`MSTTSLocJaJP.dat` 结构与中文完全一致，字符→嵌入行号映射是从
`FUN_1802548ec` / `FUN_180254c78` 反编译出的分段公式；同样用 hook 验证
**54/54 字符类别 100% 一致**。日语剩余差距是音高重音记号（`o1`/`kyo1`），属另一个模型。

### 7.6 词表重标定：一个"探针文件乱序"的坑

多语种词表需要补读音，最直接的办法是让引擎把每个词单独合成、从 ORT 探针抓 ids。
但批量跑时发现：**探针文件会错位**。引擎的推理是异步的，文件出现顺序和请求顺序不一致，
于是「词 A 的 ids」可能被写成「词 B 的读音」，词表里出现大量 `en-us_*` 符号堆叠。

解决办法是加一道**哨兵屏障**：

```
请求 word → 请求哨兵文本 "zzzqqq"
等两个文件都出现 → 按文件名里的计数器 cNN 排序
哨兵文件的前一个文件 = word 的 ids
```

哨兵签名（`z - e1 - z - e1 ...`）先实测得到；找不到哨兵就重试。
加上这个协议后，703 个德语词一次跑完 0 失败，如 `hallo → h a - l ow1`、
`system → z uy s - t ey1 m`，与引擎完全一致。

这个坑的教训：**做"引擎当老师"的数据采集时，时序/缓存/并发细节比算法更容易出错**，
而错误数据会静默污染词表。

### 7.8 英文大规模标定（自然句 500 + TN 压力集 102，进行中）

138 句太少，英文单独扩了一批数据：从公版小说抽 500 句自然句，再写 102 句 TN 压力句
（数字、货币、日期、时间、单位、分数、缩写、电话号码、路径/邮箱），全部用引擎 fast 探针
抓 encoder 输入 id。然后干了两件事：

1. **引擎读音直接标定**：从这 602 句的引擎输出里对齐出 1402 个词的「句内读音」（包含
   and→ae1 n、to→t uh、of→ah1 v、the 的两种弱读等），再用隔离探针补 2038 个词的单字读音；
2. **英文前端按引擎规则重写**：连字符复合词算一个词（词内用 `-` 分音节）、括号/分号/冒号
   的停顿编码、罗马数字（Chapter V → five）、缩写（Mrs. → misiz）、部分 TN（1,234,567 →
   one million two hundred and thirty four thousand five hundred and sixty seven dollars、
   101 → one hundred and one、$5.99 → five dollars and ninety nine cents 等）。

效果：英文自然句逐 id 一致率 **17.8% → 99.0%（495/500）**，TN 压力集 **5.9% → 97.1%（99/102）**，
另抽三本不同作者的书做 500 句 holdout：词表补标定前 34%，补 1300 词后 **95.0%（475/500）**；
8 语种 golden 仍是 138/138；40 个异读词（present/record/address…）按上下文选读音，80 句异读测试全过。TN 里货币/日期/时间/单位/分数/罗马数字/电话分组/缩写点号
都已经按引擎实测行为实现，剩下的是电话三位分组、版本号、引号短语这类长尾。

## 8. 踩过的坑（真实的逆向日常）

- **ORT 符号 shape 冲突**：最后用"每块静态图"绕过；
- **缓存/补零/量化细节**：音频对不上时，用逐层张量对拍定位；
- **Python `hash()` 随机化**：模型特征哈希跨进程不一致，导致训练/推理对不上，换成 `crc32` 才对；
- **探针缓存污染**：同一文本第二次请求直接命中引擎缓存，没有新的 encoder 输入——
  必须重启进程或换文本；
- **临时目录被清空**：语音包一度被系统清理，只能从备份 zip 恢复；
- **采集进程假死**：探针文件索引间距变大导致检测逻辑卡住，改成"先小步试探再目录扫描"；
- **版本差异**：不同音色包符号 ID 完全不同，所有数据都改成符号名存储。

这些坑本身也说明一件事：**"逐采样一致"不是靠一个漂亮思路，而是靠大量对照实验**。
